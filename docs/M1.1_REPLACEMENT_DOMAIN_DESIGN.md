### 1. Verdict

Рекомендуется **одна новая domain-сущность `ReplacementNeed`** и одно аддитивное поле `Entity.usage` (`active|spare`). Без изменения основной Entity сценарий технически возможен через отдельную таблицу состояния, но выбранный вариант минимизирует число сущностей и хранит состояние вещи в самой Entity. Новая покупка остаётся обычной Entity; архив задаётся исключительно `Entity.archived`, параллельного каталога нет. Проект готов к реализации после одного продуктового решения об ограничении первого сценария количеством `1` (§11); исходники не изменялись.

### 3. Proposed domain model

Все положения ниже — предлагаемое поведение. Сейчас Homebox не хранит replacement need, её причину, требования, переход source→purchase или различие active/spare; существующие данные Entity перечислены в `Entity.Fields/Edges` выше.

**Новая сущность: `ReplacementNeed` / таблица `replacement_needs`.** Назначение всегда «заменить конкретную вещь»; отдельное поле kind и общий wishlist не нужны.

| Поле | Тип | NULL | Назначение / ограничение |
| --- | --- | --- | --- |
| `id` | UUID | NOT NULL | PK; клиент создаёт UUID один раз на намерение и сохраняет при повторах |
| `group_id` | UUID | NOT NULL | FK → `groups.id`; задаётся сервером из tenant context, immutable |
| `source_entity_id` | UUID | NOT NULL | FK → `entities.id`; immutable |
| `reason` | string, 1–255 символов | NOT NULL | Непустая причина; назначение «замена» задано самим типом need, таксономию причин сейчас не вводим |
| `requirements` | string, до 1000 символов | NULL | Необязательная заметка/требования; пустое значение нормализуется в NULL |
| `status` | enum `open|completed|cancelled` | NOT NULL | Default `open`; терминальные состояния не редактируются |
| `replacement_entity_id` | UUID | NULL | FK → `entities.id`; заполнен только после успешного completion |
| `source_disposition` | enum `active|spare|archived` | NULL | Исторический выбор при completion; не текущее состояние старой вещи |
| `completion_fingerprint` | string, 64 hex-символа | NULL | SHA-256 нормализованного входа complete для проверки совместимости повторов |
| `created_at` | timestamp | NOT NULL | Время создания, immutable; `BaseMixin` |
| `updated_at` | timestamp | NOT NULL | Время последнего перехода; после terminal status неизменно |

Отдельный completed_at не нужен: для completed `updated_at` фиксирует момент завершения. Поля создания `source_entity_id`, `reason`, `requirements` неизменяемы, что позволяет сравнивать повторный create с исходным запросом без второго fingerprint.

**Ограничения БД и владение ссылками:**

- Частичный UNIQUE `(group_id, source_entity_id)` для `status=open`. Причина не входит в ключ: разные reason не позволяют незаметно открыть две замены одной вещи.
- UNIQUE для ненулевого `replacement_entity_id`: одна приобретённая Entity является результатом одного completion. Она может позже выступить source другого need.
- CHECK: при `completed` одновременно заполнены replacement ID, disposition и fingerprint; при `open/cancelled` все три NULL. Source и replacement ID различаются. Значения enum и длины должны проверяться и на входе, и в схеме/миграциях.
- FK source/replacement — RESTRICT при удалении. Связь с группой — CASCADE; штатное удаление всей группы сначала удаляет её needs в той же транзакции, затем Entity. Случайный individual DELETE не стирает историю.
- Обычные FK на ID не доказывают равенство групп. Repository внутри транзакции проверяет все ссылки с authenticated gid; новая Entity создаётся с тем же gid. Клиент не передаёт group и replacement ID, смена владельца или source у need запрещена. Дополнительные composite FK/индексы основной Entity не требуются для выбранного API.
- Ent и обе Goose-миграции должны одинаково выражать FK, CHECK и partial UNIQUE. Для explicit FK использовать соглашение `backend/internal/data/ent/schema/maintenance_entry.go` — `MaintenanceEntry.Fields/Edges`; UUID/timestamps — `BaseMixin`.

**Расширение существующей Entity:** `usage`, enum `active|spare`, NOT NULL, default `active`; существующие записи получают `active`. Effective lifecycle: `archived=true` → archived, иначе значение usage. В таблице need disposition — факт выполненной команды; по нему никогда не вычисляется текущее состояние вещи.

`usage` возвращается в существующем Entity DTO; для последующего переключения active/spare достаточно необязательного поля существующего PATCH. Отсутствующее поле в старых клиентах не сбрасывает usage; PUT также сохраняет его при отсутствии. Generic archive/unarchive сохраняет usage: архив маскирует его, разархивация возвращает прежнее active/spare. При disposition=archived completion меняет только archived; это же правило действует и здесь.

**Граница первой версии, до подтверждения §11:** source — обычная неархивная Entity, не location, без ненулевого sold_date, `quantity=1`; replacement также обычная Entity с `quantity=1`, `archived=false`, `usage=active`. Источник может быть active или spare. Количество старой вещи не уменьшается: сохранение двух физических вещей отражается двумя Entity, а не потребностью как ещё одной вещью. Homebox допускает дробное/множественное quantity (`repo_entities.go` — `validateQuantity`, `EntityCreate`); ограничение вводится только для replacement-сценария.

### 4. State machines

**Need:** `open → completed` только через complete; `open → cancelled` через cancel. Повторы completed/cancelled возвращают прежний результат; `completed → cancelled`, `cancelled → completed` и reopen запрещены. Новый цикл замены — новый UUID при отсутствии другого open need.

**Вещь:** active ↔ spare через usage; active/spare → archived через штатный archived; разархивация возвращает сохранённый usage. Completion обязательно получает один явный disposition: active, spare или archived. Новая Entity всегда начинает с active; completed need не управляет последующими изменениями обеих Entity.

Архивирование, продажа или изменение quantity source при открытом need не закрывают потребность автоматически. Она остаётся open; complete возвращает `409`, пока source не удовлетворяет предусловиям, cancel остаётся доступен. Источник или приобретённую Entity нельзя удалить, пока на них ссылается сохранённый need любого статуса; отмена сохраняет историю и не снимает FK.

### 5. Transaction: complete replacement

**Граница — новая `ReplacementNeedRepository.Complete`**, одна Ent-транзакция. Controller получает DTO/gid; `ReplacementNeedService.Complete` применяет политику сценария и вызывает repository-команду. Repository владеет begin/commit/rollback и tx-aware Entity helpers; service не запускает отдельные публичные Create/Patch.

Основание: `EntityRepository.Create` пишет через `r.db`; `Patch`, `Duplicate`, `CreateFromTemplate` открывают собственные транзакции (`backend/internal/data/repo/repo_entities.go`, одноимённые методы). `resolveDefaultEntityType` способен создать тип через `r.db`, а `EntityService.Create` отдельно назначает AssetID (`backend/internal/core/services/service_entities.go` — `Create`): простая обёртка этих вызовов не даёт атомарности.

1. До begin валидировать форму команды и получить canonical fingerprint. Начать `db.Tx`; установить deferred rollback при любом неуспехе.
2. Прочитать need по `(gid,id)`. Чужой/отсутствующий → `404`. Для completed сравнить fingerprint и вернуть сохранённый terminal DTO либо `409`; не проверять заново изменившееся состояние source. Для cancelled → `409`.
3. Получить write lock на строку source по ID+gid, затем перечитать need и актуальную source. Реализация должна работать с обоими dialects: транзакционная блокировка записи/no-op UPDATE, без нового lock/version-поля. Повторно проверить terminal status и предусловия source; не опираться на чтение до ожидания блокировки.
4. В той же транзакции проверить все переданные parent/location/type/tag ссылки новой Entity через tx clients и текущий gid. Тип новой Entity не должен быть location. Определить default type и AssetID внутри tx: использовать tx-aware варианты существующих helpers, включая `GetHighestAssetIDTx`; AssetID не является ключом идемпотентности.
5. Создать **одну** обычную Entity через внутренний `CreateTx`: `EntityCreate`, quantity=1, active, неархивная. Не копировать source, attachments, templates или sold-данные; не выполнять filesystem/network операции. Для первого slice «покупка» означает регистрацию приобретённой Entity, цена/магазин не обязательны; EntityCreate сейчас не содержит purchase_* (`repo_entities.go` — `EntityCreate`, `EntityUpdate`).
6. Узким tx-update установить старой Entity выбранный usage или archived. Не вызывать полный PUT с ранее прочитанным снимком и не перезаписывать другие поля.
7. Условным обновлением need по `(gid,id,status=open)` одновременно записать completed, replacement ID, disposition, fingerprint и updated_at; требовать ровно одну изменённую строку. Ноль строк → rollback всех записей, включая новую Entity, затем отдельное чтение актуального need для replay/conflict. Промежуточный persisted status не нужен.
8. Сформировать DTO из результатов транзакции, commit; только после успешного commit публиковать штатное mutation event группы. Потеря ответа или ошибка после commit решается повтором по тому же need ID. До commit никаких событий об успешной замене.

Ошибка любого шага откатывает новую Entity, lifecycle старой, need, связи и возможный default type. При busy/serialization failure транзакция целиком откатывается; вернуть retryable `409`, не повторять отдельные записи и не считать операцию завершённой. При неопределённом исходе commit — ошибка и безопасный повтор тем же ID; новая попытка сначала читает сохранённый status. Создание need также использует source lock и partial UNIQUE; cancel — условный переход open→cancelled.

**Обязательная интеграция удаления:** недостаточно добавить RESTRICT и обработать ошибку в конце. Сейчас `EntityRepository.Delete/DeleteByGroup`, `GroupRepository.GroupDelete` и `AttachmentRepo.Delete` могут удалить attachment files до удаления Entity (`repo_entities.go`, `repo_group.go`, `repo_item_attachments.go`, соответствующие методы). Поэтому проверка replacement-ссылок должна происходить **до любых внешних изменений**, под той же блокировкой Entity, которую берёт создание need; блокировку держать до DB-удаления. Bulk/wipe блокирует цели в стабильном порядке и проверяет все ссылки до удаления maintenance/attachments. GroupDelete под блокировками целей удаляет свои needs перед Entity. Это локальная защита нового FK-инварианта; общая переработка storage не входит в slice. Без общей блокировки простой preflight оставляет гонку create need ↔ delete.

### 6. Idempotency

- Один механизм: долговечная идентичность команды через **need UUID**, без отдельной таблицы запросов и Idempotency-Key.
- Create получает клиентский UUID; повтор того же UUID с теми же immutable полями возвращает существующий need, даже completed/cancelled. Другой payload → `409`, новый need не создаётся.
- Новый UUID при другом open need того же source → `409`; защита — partial UNIQUE, не только предварительный SELECT.
- Complete использует UUID из URL; conditional status update допускает единственный commit, проигравшая транзакция откатывает свою новую Entity.
- Сохранять SHA-256 canonical JSON принятого DTO: фиксированная нормализация v1, отсортированные уникальные tagIds, единые значения отсутствующих nullable полей; неизвестные поля отклонять. Хеш включает newEntity и disposition, но не серверные ID/время/AssetID.
- Completed + тот же fingerprint → `200` и прежние replacement ID/disposition/updated_at; другой fingerprint → `409`. Replay проверяется до валидации изменяемого состояния Entity.
- Cancel повторяем: cancelled → прежний DTO, completed → `409`; он не очищает следы выполненного completion.
- Потерянный ответ, перезапуск сервера и конкурентные запросы не меняют контракт. Внутрипроцессный mutex или AssetID этой гарантии не заменяют.

### 7. Minimal API

Все новые маршруты под штатными `userMW`/RoleUser: `Authorization: Bearer …`, JSON; tenant определяется `mwTenant`, включая штатный `X-Tenant` или default group. Основание: `backend/app/api/routes.go` — `userMW`, entity routes; `backend/app/api/middleware.go` — `mwTenant`; `handlers/v1/v1_ctrl_entities.go` — `HandleEntitiesCreate`, `HandleEntityGet`.

| Method | Path | Purpose | Input | Result |
| --- | --- | --- | --- | --- |
| POST | `/api/v1/replacement-needs` | Создать потребность | `id` UUID, `sourceEntityId` UUID, `reason` string, optional `requirements` | `201` Need; совместимый replay `200`; active duplicate или конфликт payload `409` |
| GET | `/api/v1/replacement-needs` | Получить активные needs tenant | Без тела; в первом slice выборка только `open` | `200`, список Need; без archived/history фильтров и отдельного GET по ID |
| POST | `/api/v1/replacement-needs/{id}/complete` | Зарегистрировать покупку, выбрать судьбу старой и закрыть need | `newEntity` — существующий EntityCreate, минимум `name`, `quantity:1`; обязательный `sourceDisposition: active|spare|archived` | `200`, terminal Need с `replacementEntityId`; такой же replay возвращает тот же результат |
| POST | `/api/v1/replacement-needs/{id}/cancel` | Отменить ошибочную/ненужную потребность | Без тела | `200`, cancelled Need; повтор `200`, completed `409` |

Need DTO содержит UUID, source ID, причину/требования, status, replacement ID, исторический disposition и timestamps; внутренний fingerprint клиенту не нужен. Entity читается существующим `GET /api/v1/entities/{id}`. Позднейшее active/spare меняется существующим PATCH Entity с добавленным optional usage, без нового lifecycle endpoint.

Отмена необходима для освобождения единственного open slot; отдельные edit, delete и generic PATCH status не нужны. Для исправления reason/requirements — cancel и новый UUID. Ошибочная форма — `400`; чужие/отсутствующие need и Entity-ссылки — одинаковый `404`; неподходящий lifecycle/quantity и терминальный конфликт — `409`. Эти статусы предлагаются для нового slice; текущий entity API не перепроектируется.

### 8. Invariants

1. Entity — единственный источник имени, quantity, tags и текущего lifecycle; таблица needs не содержит их копий. Создание need не меняет inventory count/quantity.
2. Для `(gid,source)` не более одного open need, независимо от reason; два конкурентных create оставляют одну запись.
3. Source/group и данные создания need immutable; повтор create с тем же UUID не создаёт запись после cancel/completion и не открывает её заново.
4. Через API/repository все source/replacement/parent/location/type/tag ссылки принадлежат gid из auth; cross-tenant запрос не оставляет записей или мутаций ни в одной группе.
5. Completed эквивалентен совместно заполненным replacement ID, disposition и fingerprint; новая Entity отлична от source и связана с результатом только одного need.
6. Успешный complete создаёт ровно одну Entity с quantity=1, active и archived=false; source.quantity сохраняется; недопустимые source/new quantity и location/sold/archive не проходят предусловия.
7. Каждый из трёх disposition устанавливает ровно выбранный effective lifecycle; архив не дублируется в новом текущем state. Sold-поля и остальные свойства source сохраняются.
8. Complete атомарен: сбой после любой записи до commit оставляет прежние source/need, число Entity и типов; mutation event об успехе отсутствует.
9. Последовательный/конкурентный одинаковый complete, включая потерю ответа, возвращает один replacement ID; другой fingerprint получает `409`, проигравшие транзакции не оставляют Entity.
10. Complete и cancel взаимоисключаются: при гонке сохраняется один terminal status; cancelled нельзя complete, completed нельзя cancel или reopen.
11. Delete связанной source/replacement получает `409` до удаления attachments, включая гонку с create need и bulk/wipe; удаление всей группы очищает её needs и Entity, не затрагивая другой tenant.
12. Archive/изменение source при open need не теряет need и повторно проверяется при complete; последующие изменения Entity не меняют terminal DTO/fingerprint и не мешают совместимому replay.

### 10. Tests required before implementation is accepted

Тесты здесь **не запускались**. Перед приёмкой соответствующего изменения нужны только адресные проверки:

- Create need: минимальный вход, requirements, UUID replay, неизменность Entity; missing/archived/sold/location source и quantity 0/дробь/>1; duplicate active с одинаковой и разной reason, включая конкурентный запрос.

- Idempotency: повтор после потерянного ответа, с новым экземпляром repository, после изменения старой/новой Entity; тот же результат и ровно одна покупка. Отличающийся payload/disposition → conflict. Повтор create после завершения/отмены не создаёт новый need.
- Конкуренция: complete/complete, complete/cancel, два create на одну source; после конфликта/rollback повторить чтение вне старого snapshot. Busy не считать успехом.
- Failure injection после создания Entity, изменения source, перед terminal update/commit; проверить rollback всех данных, default type и отсутствие post-commit event. Отдельно потеря ответа после commit: replay без дубля.
- Cross-tenant: чужие need/source, parent/location/type/tag, подмена gid в JSON, новый UUID на чужую source; одинаковый `404`, никаких побочных записей. Проверить обычные auth/RoleUser границы нового API.

- Точечные HTTP/controller tests только четырёх новых маршрутов: статусы, JSON DTO и ошибки. Без запуска frontend, Playwright или полного runtime для этой проектной задачи.
