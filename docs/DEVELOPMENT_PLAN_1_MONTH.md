# План разработки первой работоспособной версии

Дата планирования: 1 октября 2026 года  
Горизонт: 1 месяц, включая риски и стабилизацию  
Целевая версия: **v0.1 — Каталог + Ревизия**

Исходные документы:

- `PRODUCT_VISION_CURRENT_ARCHITECTURE.md`
- `TECH_STACK.md`

Этот документ является планом поставки продукта, а **не декомпозицией задач для coding-агентов**. Декомпозицию недельных этапов на конкретные агентские задачи выполняет технический отдел.

---

## 1. Цель месяца

За один месяц получить первую версию, которой можно реально пользоваться для учета одежды, обуви и личного спортивного/туристического снаряжения.

Главная доказанная ценность версии:

> Пользователь ведет понятный каталог вещей и может поддерживать его достоверность через удобную возобновляемую ревизию, не превращая учет в отдельную работу.

В конце месяца приложение должно:

- запускаться локально и на собственном сервере;
- нормально работать с мобильного браузера;
- хранить данные в PostgreSQL;
- позволять вести каталог вещей и количественных групп;
- позволять использовать категории, назначения, климатическую применимость и простое состояние;
- хранить базовые размерные данные вещи и параметры пользователя;
- позволять провести ревизию выбранной категории;
- сохранять прогресс незавершенной ревизии;
- продолжать ревизию после перерыва;
- накапливать изменения ревизии до завершения;
- атомарно применять результат завершенной ревизии;
- фиксировать дату последней полной проверки категории;
- не считать непроверенную категорию подтвержденно пустой.

## 2. Жесткая граница v0.1

### Входит в обязательный объем

1. Категории с неглубокой иерархией.
2. Готовый базовый набор категорий, который можно расширять и редактировать.
3. Каталог вещей.
4. Индивидуальные вещи.
5. Группы взаимозаменяемых вещей с количеством.
6. Единая простая шкала состояния.
7. Несколько назначений у одной вещи.
8. Практическая климатическая применимость.
9. Базовые размеры/характеристики вещи.
10. Профиль пользовательских замеров.
11. Ручное добавление и редактирование вещей.
12. Просмотр каталога с базовыми фильтрами.
13. Режим ревизии конкретной категории.
14. Сохранение и восстановление прогресса ревизии.
15. Проверка наличия и состояния индивидуальной вещи.
16. Проверка количества и состояния grouped-записи.
17. Добавление новой найденной вещи из режима ревизии.
18. Отложенное применение удаления/уменьшения количества до завершения ревизии.
19. Атомарное завершение ревизии.
20. Дата последней полной проверки категории.
21. Mobile-friendly web UX.
22. Docker Compose deployment.
23. Работа через LAN/VPN без собственной auth.
24. Backend/API, не завязанный на Vue-клиент.

### Не входит в обязательный объем

В течение этого месяца **не разрабатываются**:

- список покупок;
- replacement workflow;
- статистика и графики;
- сложный полнотекстовый поиск;
- AI/LLM-поиск;
- автоматическое распознавание вещей;
- парсинг интернет-магазинов;
- полноценный offline/PWA режим;
- offline mutations;
- нативное iOS-приложение;
- multi-user;
- публичная регистрация;
- роли и tenant-модель;
- OAuth/OIDC;
- собственная auth в начале месяца;
- Redis;
- фоновые worker'ы;
- отдельный search engine;
- S3/MinIO;
- Kubernetes;
- сложная observability-инфраструктура.

### Stretch, только если основной объем стабилен

Следующие вещи разрешены только после прохождения всех критериев v0.1:

- простая загрузка фотографий в filesystem volume;
- read-only cache уже загруженных данных;
- небольшие UX-улучшения каталога;
- дополнительные фильтры;
- первые подготовительные точки для будущей простой auth.

Они не должны сдвигать релиз.

## 4. Рабочие принципы месяца

### 4.1. Вертикальные результаты важнее инфраструктурной полноты

Каждая неделя должна завершаться исполняемым, проверяемым состоянием продукта.

Не допускается ситуация, когда к концу третьей недели существует много инфраструктуры, но нельзя добавить вещь или пройти ревизию.

### 4.2. Работа идет по критическому пути

Критический путь:

```text
Исполняемый каркас
    ↓
Каталог end-to-end
    ↓
Ревизия end-to-end
    ↓
Стабилизация + deployment + mobile UX
```

Любая задача вне этого пути должна доказывать, что без нее v0.1 невозможно выпустить.

### 4.3. Ревизия — главный функциональный риск

Она содержит:

- незавершенное состояние;
- прогресс;
- staged changes;
- grouped quantity;
- добавление новой вещи;
- атомарное завершение;
- доверие к категории после завершения.

Поэтому ревизия получает отдельную неделю разработки и дополнительный резерв в четвертой неделе.

### 4.4. Сначала корректность, потом удобства

Особенно для:

- quantity;
- staged removal;
- завершения ревизии;
- повторного открытия приложения;
- сохранения прогресса;
- транзакций.

### 4.5. Не строить будущее заранее

Если функция не требуется для `Каталог + Ревизия`, она не должна определять текущую схему и инфраструктуру без очень сильной причины.

### Результат недели

К концу недели пользователь должен иметь возможность открыть приложение с телефона и:

- пройти по категориям;
- увидеть вещи выбранной категории;
- создать индивидуальную вещь;
- создать количественную группу;
- изменить вещь;
- убрать вещь из текущего каталога;
- указать состояние;
- указать количество;
- назначить несколько сценариев использования;
- указать климатическую применимость;
- заполнить базовые размеры/характеристики;
- заполнить пользовательские замеры;
- отфильтровать каталог по основным структурированным признакам;
- увидеть, когда категория в последний раз была полностью проверена, даже если значение пока отсутствует.

### Что должно быть разработано

#### Categories

- отображение дерева;
- получение категории;
- базовое создание/редактирование пользовательской структуры;
- готовая структура по умолчанию;
- понятное поведение дочерних категорий.

#### Catalog

- list/read/create/update;
- индивидуальная запись;
- grouped-запись с quantity;
- единое condition;
- purposes many-to-many или эквивалентная нормализованная модель;
- climate;
- базовые размерные поля;
- дополнительные JSONB-атрибуты;
- текущая/неактивная запись в объеме, необходимом для скрытия выбывших вещей из обычного каталога.

Подробная история причин выбытия не требуется.

#### Profile measurements

- один текущий профиль;
- хранение пользовательских замеров;
- редактирование;
- контекстное отображение релевантных параметров там, где это уже очевидно из категории.

Полноценная multi-profile модель не требуется.

#### Catalog UI

- mobile-first список;
- карточка/детали вещи;
- формы create/edit;
- grouped quantity UX;
- condition UX;
- categories;
- purposes;
- climate;
- basic filters;
- user measurements.

Главная цель интерфейса — быстрое ручное использование, не дизайнерская завершенность.

#### API contract

Все реализованные операции доступны через REST/JSON и отражаются в OpenAPI.

Frontend использует generated TypeScript contract; ручное дублирование DTO не допускается.

Неделя завершена, если вручную с мобильного браузера проходит следующий сценарий:

1. открыть каталог;

3. добавить индивидуальную вещь;
4. добавить группу с quantity > 1;
5. изменить состояние;
6. изменить количество группы;
7. назначить несколько purposes;
8. указать climate;
9. заполнить размеры;
10. открыть запись после перезапуска приложения и увидеть сохраненные данные;
11. скрыть выбывшую вещь из обычного каталога;
12. отфильтровать каталог по основным признакам.

- item/group distinction;
- quantity;
- condition;
- categories;
- purposes;

## Неделя 3 — Ревизия end-to-end

**Период:** 15–21 октября  
**Цель:** реализовать главную отличительную функцию v0.1.

### Продуктовое поведение ревизии

Ревизия запускается для **конкретной категории** и охватывает согласованную область этой категории, включая ее дочерние элементы каталога, если они входят в выбранную category scope.

Ревизия:

- не ограничена по времени;
- имеет состояние «в процессе»;
- сохраняет прогресс;
- может быть закрыта вкладка/браузер;
- может быть продолжена позже с сохраненного места;
- не подтверждает категорию до явного завершения.

Во время ревизии:

#### Для индивидуальной вещи

Пользователь подтверждает:

- вещь есть;
- вещь отсутствует;
- актуальное состояние.

#### Для grouped-записи

Пользователь подтверждает:

- фактическое количество;
- общее состояние.

#### Новая вещь

Найденную, но отсутствующую в каталоге вещь можно добавить прямо из режима ревизии.

Она считается проверенной в рамках текущей ревизии.

#### Staged changes

До завершения ревизии:

- отсутствие индивидуальной вещи не должно окончательно удалять/скрывать ее из подтвержденного каталога;
- уменьшение quantity не должно окончательно применяться;
- незавершенная ревизия не обновляет дату полной проверки категории.

#### Completion

Завершение ревизии должно одной бизнес-операцией:

- применить staged absence;
- применить staged quantity;
- применить обновленные состояния;
- сохранить новые вещи;
- завершить revision session;
- обновить дату последней полной проверки категории.

Операция должна быть атомарной в PostgreSQL.

### Что должно быть разработано

#### Revision backend

- запуск ревизии;
- чтение текущего состояния;
- сохранение прогресса;
- запись решения по конкретной вещи;
- grouped quantity result;
- condition result;
- поддержка новой вещи внутри процесса;
- восстановление текущей позиции/прогресса;
- завершение;
- транзакционная атомарность completion;
- защита ключевых инвариантов на DB/application уровне.

#### Revision frontend

- вход в режим ревизии из категории;
- понятный индикатор прогресса;
- быстрое подтверждение individual item;
- быстрое подтверждение grouped item;
- изменение condition;
- ввод фактического quantity;
- добавление новой вещи;
- выход без потери прогресса;
- продолжение незавершенной ревизии;
- экран/действие явного завершения;
- понятное отображение последней завершенной проверки категории.

### Критические тестовые сценарии

Обязательны проверки:

1. старт ревизии;
2. перезапуск приложения и продолжение;
3. individual present;
4. individual absent;
5. grouped quantity unchanged;
6. grouped quantity decreased;
7. grouped quantity = 0;
8. condition changed;
9. новая вещь добавлена в процессе;
10. незавершенная ревизия не подтверждает категорию;
11. незавершенное removal не изменяет подтвержденный каталог окончательно;
12. completion применяет все изменения совместно;
13. ошибка completion не оставляет частично примененную ревизию;
14. после completion обновляется дата проверки;
15. повторное чтение после completion показывает новое состояние каталога.

### Критерии выхода из недели

Неделя завершена только когда один реальный сценарий проходит end-to-end:

1. открыть категорию с несколькими индивидуальными и grouped-вещами;
2. начать ревизию;
3. подтвердить несколько вещей;
4. изменить condition;
5. уменьшить quantity группы;
6. отметить индивидуальную вещь отсутствующей;
7. добавить новую вещь;
8. закрыть приложение;
9. открыть приложение снова;
10. продолжить с сохраненного прогресса;
11. завершить ревизию;
12. увидеть корректно примененный каталог;
13. увидеть обновленную дату полной проверки категории.

Если этот сценарий ненадежен, неделя не считается завершенной независимо от количества написанного кода.

### Резерв риска недели

Не менее **20% недели** следует считать резервом именно на:

- транзакционную семантику;
- прогресс;
- edge cases quantity;
- состояние после browser refresh;
- frontend invalidation/cache;
- ошибки при completion.

## Неделя 4 — Стабилизация, мобильный UX и релиз

**Период:** 22–31 октября  
**Цель:** превратить работающие feature в версию, которой можно пользоваться ежедневно.

Последние дни месяца сознательно являются частью risk budget, а не местом для добавления нового scope.

### 4.1. Интеграционная стабилизация

Проверяется совместная работа:

- categories;
- catalog;
- profile;
- revision;
- OpenAPI generation;
- production build;
- migrations;
- PostgreSQL;
- Docker Compose.

Исправляются:

- inconsistent validation;
- stale frontend cache;
- ошибки навигации;
- некорректные error states;
- проблемы повторного открытия;
- migration/build regressions.

### 4.2. Mobile UX pass

Обязательно проверить реальные сценарии на узком мобильном экране.

Особое внимание:

- размер hit targets;
- формы;
- selects;
- dialogs;
- scrolling;
- keyboard interaction;
- быстрое изменение quantity;
- быстрое изменение condition;
- revision flow;
- отсутствие действий, требующих desktop hover;
- понятность back/navigation behavior.

Цель — аккуратный рабочий интерфейс, не визуальный perfectionism.

### 4.3. Production deployment

Должно быть подтверждено:

- clean Docker Compose startup;
- migrations при новой установке;
- persistent PostgreSQL volume;
- production static frontend;
- restart без потери данных;
- доступ по LAN/VPN;
- конфигурация через environment;
- инструкция backup PostgreSQL;
- инструкция восстановления/перезапуска в необходимом минимальном объеме.

### 4.4. Data safety

До релиза обязательны:

- проверка destructive operations;
- проверка revision completion rollback;
- проверка backup;
- проверка migration from предыдущей migration revision;
- отсутствие `create_all()` как production migration path.

### 4.5. Acceptance pass

Перед релизом вручную выполняется полный пользовательский сценарий:

#### Каталог

- создать категории/использовать seed;
- создать несколько вещей;
- создать grouped-запись;
- изменить основные данные;
- заполнить профиль размеров;
- отфильтровать каталог;
- перезапустить приложение;
- убедиться в сохранности данных.

#### Ревизия

- начать ревизию;
- обработать individual item;
- обработать grouped item;
- изменить condition;
- уменьшить quantity;
- отметить item отсутствующим;
- добавить новую вещь;
- прервать;
- продолжить;
- завершить;
- проверить итог каталога;
- проверить дату категории.

#### Deployment

- собрать production;
- поднять чистую установку;
- открыть приложение с мобильного браузера через LAN/VPN;
- выполнить основные операции.

### 4.6. Risk buffer

Последние **3–4 дня месяца** нельзя заранее занимать дополнительными feature.

Они зарезервированы под:

- непредвиденные bugs;
- transaction issues;
- migration issues;
- mobile regressions;
- deployment;
- доработку revision UX.

Если резерв не понадобился, разрешены только низкорисковые улучшения.

# 6. Критерии готовности v0.1

Версия считается выпущенной только если одновременно выполнены следующие условия.

## Product

- каталог реально пригоден для ручного использования;
- есть индивидуальные и grouped-записи;
- category navigation работает;
- condition работает;
- purposes работают;
- climate работает;
- размеры/характеристики хранятся;
- профиль замеров работает;
- ревизия запускается;
- ревизия сохраняет прогресс;
- ревизия продолжается после перерыва;
- ревизия корректно обрабатывает individual/group;
- новая вещь может быть добавлена из ревизии;
- completion атомарно применяет результат;
- категория получает дату последней полной проверки;
- незавершенная ревизия не выдает категорию за проверенную.

## UX

- основные сценарии работают на мобильном экране;
- создание вещи не требует длинного обязательного заполнения;
- ревизия не заставляет редактировать всю карточку;
- navigation понятна без документации;
- errors имеют понятное пользовательское состояние;
- после reload пользователь не теряет незавершенную ревизию.

## Backend

- PostgreSQL — единственная БД;
- Alembic migrations поднимают пустую БД;
- transaction boundaries явные;
- completion revision покрыт targeted tests;
- API отражен в OpenAPI;
- API DTO не дублируются вручную во frontend.

## Frontend

- TypeScript build проходит;
- generated API types актуальны;
- TanStack Query корректно invalidates измененные данные;
- нет обязательной зависимости от глобального store;
- frontend production build обслуживается backend-приложением.

## Deployment

- Docker Compose поднимает приложение;
- данные переживают restart;
- имеется инструкция запуска;
- имеется минимальная инструкция backup;
- приложение доступно по LAN/VPN;
- собственной auth пока нет и приложение не предполагается публиковать напрямую в интернет.

# 8. Правила управления отклонением от графика

Если проект начинает отставать, сокращение идет в следующем порядке:

1. декоративная полировка;
2. количество фильтров;
3. удобство редактирования дополнительных JSONB attributes;
4. необязательные фотографии;
5. дополнительные seed-данные;
6. второстепенные frontend tests;
7. любые stretch goals.

Нельзя вырезать ради срока:

1. корректную persistence-модель;
2. migrations;
3. индивидуальный + количественный учет;
4. состояние;
5. categories;
6. revision resume;
7. staged changes;
8. atomic completion;
9. last verified category state;
10. mobile usability основного flow;
11. production Compose.

Если к середине недели 4 ревизия не стабильна, работа над любыми вторичными функциями прекращается полностью.

# 9. Стратегия тестирования

## Backend

Приоритет:

1. DB constraints;
2. use-case tests;
3. revision transaction tests;
4. API contract tests;
5. migration smoke tests.

Тесты persistence выполняются против реального PostgreSQL.

## Frontend

Приоритет:

1. нетривиальные forms/state transitions;
2. revision progress;
3. resume behavior;
4. mutation/query invalidation;
5. critical components.

Не требуется unit-test каждый простой визуальный компонент.

## End-to-end

Большой E2E-suite в этот месяц не строится.

Но к релизу обязательно должен существовать воспроизводимый ручной acceptance scenario, описанный в этом плане.

Если технический отдел сочтет небольшой автоматизированный smoke E2E дешевым и надежным, он допустим, но не должен становиться отдельным инфраструктурным проектом.

# 10. Принцип работы технического отдела и агентов

Этот план определяет:

- цель;
- недельный scope;
- обязательные результаты;
- invariants;
- критерии приемки;
- границы v0.1.

Он **не определяет конкретные агентские задачи**.

Технический отдел должен для каждого недельного этапа:

1. определить технические зависимости;
2. выделить независимые или последовательно исполнимые работы;
3. определить границы изменения файлов/feature;
4. сформулировать агентские задания;
5. определить проверки для каждого задания;
6. организовать интеграцию результатов;
7. не разрешать агентам самостоятельно расширять продуктовый scope или менять зафиксированный стек.

Предпочтительно, чтобы агентские задания были локализованы по feature и имели проверяемый результат.

# 11. Контрольные точки месяца

## Gate A — конец недели 1

**Вопрос:** существует ли воспроизводимый проект, который можно развивать?

Если нет — нельзя компенсировать это написанием feature поверх нестабильного фундамента.

## Gate B — конец недели 2

**Вопрос:** можно ли уже реально вести каталог без ревизии?

Если нет — ревизия не должна маскировать незавершенность каталога.

## Gate C — конец недели 3

**Вопрос:** можно ли пройти полный revision flow с перерывом и продолжением?

Если нет — неделя 4 начинается со стабилизации revision, не с нового scope.

## Gate D — конец месяца

**Вопрос:** можно ли развернуть приложение и пользоваться им с телефона без участия разработчика в каждом запуске?

Только после положительного ответа версия считается v0.1.

# 12. Результат после месяца

Успешный результат — не «готовая платформа» и не «полный менеджер гардероба».

Успешный результат:

> Персональное self-hosted web-приложение, в котором можно вести структурированный каталог одежды, обуви и личного снаряжения и периодически подтверждать его достоверность через возобновляемую ревизию категории.

Это достаточная основа, чтобы начать реальное использование и уже на фактическом опыте решать, что должно стать следующим этапом: покупки, статистика, улучшенный поиск, фотографии, auth или другие функции.
