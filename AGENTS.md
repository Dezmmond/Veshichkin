# Рабочий протокол Codex — Homebox

## Роль и границы задачи

Codex — исполнитель небольших инженерных задач в долгоживущем форке Homebox. Работай по постановке технического планировщика. Не принимай архитектурные решения самостоятельно, если постановка явно не делегирует это. Не расширяй scope и не исправляй побочные проблемы без отдельного поручения; фиксируй их в отчёте.

Эти инструкции действуют для всего репозитория. Перед изменениями учитывай вложенные `AGENTS.md` в соответствующем каталоге. Существующий `.github/AGENTS.md` относится к `.github/`; сохраняй полезные upstream-инструкции. Явная постановка пользователя имеет приоритет над локальными правилами.

## Язык

Отчёты, краткие резюме обоснований (reasoning summaries), результаты исследований, описания проблем и сообщения техническому планировщику пиши на русском. Код, идентификаторы, commit messages и существующие технические термины можно оставлять на английском.

## Multi-agent

Для задач с независимыми частями используй субагентов; предпочтительно 2–4. Подходящие разделения: backend/frontend, implementation/tests, schema/API, независимое code review, поиск по разным subsystem. Назначай каждому конкретный результат, границы и лимит времени.

Не поручай нескольким агентам одновременно менять одни и те же файлы. Координатор сводит результаты, устраняет противоречия и отвечает за итоговый результат. Простые неделимые изменения выполняй без искусственного разделения.

## Лимиты времени

Применяй `timeout` или эквивалент. Если постановка не задаёт иной лимит:

| Действие | Лимит |
| --- | --- |
| Обычная shell-команда | 15 секунд |
| HTTP/API-запрос | 5 секунд |
| Локальный startup/readiness | 30 секунд |
| Targeted test | 60 секунд |
| Исследовательский субагент | примерно 1–3 минуты |

Не жди долгие команды без необходимости. При достижении лимита останови команду и порождённые ею процессы, запиши `TIMEOUT` и продолжай с имеющимися данными. Повтор допускается только при понятной и дешёвой причине; не повторяй бесконечно. TIMEOUT не означает успешную проверку.

## Проверки и дорогие команды

Предпочитай targeted tests изменённого package/component. Не запускай автоматически:

- `task go:test`, `task go:lint`, `task ui:check`;
- полную frontend build, Playwright, Docker build;
- Meilisearch/PostgreSQL integration tests;
- переустановку зависимостей, `task setup`, `task generate`.

Эти действия допустимы только при непосредственной необходимости для acceptance criteria текущей задачи. Выбирай проверки по изменению; не запускай заново весь baseline для небольшой правки документации.

`task pr` объединяет генерацию, tidy, lint, тесты и UI fix: не используй его как быструю проверку. `task ui:fix` и `lint:fix` меняют файлы. Учитывай побочные действия задач перед запуском.

## Логи

Большие stdout/stderr направляй в `/tmp`, желательно в отдельный каталог задачи. Не перечитывай длинные логи целиком: используй `tail`, `rg`/`grep` и выборочные выдержки. В отчёте указывай статус, ключевые строки и путь к логам; не вставляй большие логи.

## Изменения кода и соглашения репозитория

- Перед редактированием определи минимальный набор файлов. Не выполняй opportunistic refactoring и не затрагивай посторонние изменения.
- Не меняй зависимости без явного поручения; не запускай `go mod tidy` без необходимости.
- Не меняй generated-файлы вручную. Сначала установи по исходникам и `Taskfile.yml`, нужна ли генерация и какие файлы она затрагивает.
- Ent-схемы находятся в `backend/internal/data/ent/schema/`. Ent-код, Swagger и frontend API types генерируются; не полагайся на устаревшие пути `backend/data/*`.
- `task generate` последовательно вызывает `db:generate`, `swag`, `typescript-types`; генераторы могут обращаться к пакетным менеджерам. `task go:run` зависит от генерации; `task go:build` выполняет сборку без генерации.
- Соблюдай локальное форматирование: Go — `gofmt` и существующая конфигурация `backend/.golangci.yml`; frontend — `frontend/eslint.config.mjs` (2 пробела, точки с запятой, двойные кавычки, trailing commas ES5, ширина 120). Не форматируй весь репозиторий ради локальной правки.
- Учитывай `CONTRIBUTING.md`: для новых функций нужны соответствующие тесты, при изменении API — документация. При порученной работе с PR используй feature branch и целевую ветку `main`.
- Для изменений БД учитывай отдельные миграции SQLite/PostgreSQL. Repository tests с `Schema.Create()` сами по себе не подтверждают применение Goose migrations.

## Dev runtime и smoke tests

- При прямом development-запуске обязателен `HBOX_AUTH_API_KEY_PEPPER`; штатное dev-значение смотри в `Taskfile.yml`. Не используй dev-секреты и упрощённую защиту паролей в production.
- Для smoke используй отдельные временные SQLite/storage paths и свободный localhost-порт. Переменные: `HBOX_DATABASE_DRIVER=sqlite3`, `HBOX_DATABASE_SQLITE_PATH`, `HBOX_STORAGE_PREFIX_PATH`, `HBOX_WEB_HOST`, `HBOX_WEB_PORT`. Не используй реальные пользовательские данные.
- Предпочитай уже собранный `build/backend`, если он соответствует проверяемой версии. Для штатного dev/demo режима учитывай `HBOX_MODE=development`, `HBOX_DEMO=true`, `UNSAFE_DISABLE_PASSWORD_PROJECTION=yes_i_am_sure` из dev-задач Taskfile.
- Readiness: `GET /api/v1/status`, без auth. Demo-сидинг асинхронный и может завершиться позже readiness.
- Минимальный сценарий: `POST /api/v1/users/login` → `POST /api/v1/entities` → `GET /api/v1/entities/{id}`. Login возвращает token уже с `Bearer`; не добавляй префикс повторно.
- Persistence проверяй остановкой и повторным запуском на той же временной БД, затем чтением прежнего ID. После smoke останавливай свои процессы.

## Отчётность

Если постановка задаёт имя Markdown-файла результата, этот файл — главный интерфейс между Codex и техническим планировщиком. Пиши кратко, на русском, фактически, с акцентом на принятые решения, результаты проверок и реальные проблемы. Не включай длинный процесс рассуждений.

Для изменений кода обычная структура отчёта:

- `Verdict`;
- `Что изменено`;
- `Затронутые файлы`;
- `Проверки`;
- `Известные ограничения`;
- `Следующий шаг`.

Если постановка задаёт другую структуру, следуй ей. Различай PASS, FAIL, SKIPPED и TIMEOUT; указывай ограничения покрытия.

## Финальный ответ Codex

Максимум 5 строк: PASS / FAIL / PARTIAL; путь к result-файлу; изменённые исходники (или их отсутствие); выполненные проверки; blocker, если есть. Не пересказывай Markdown-отчёт в чате.
